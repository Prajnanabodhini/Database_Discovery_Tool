Use these steps in order

Recommended
  1. Dry RunChecks the tool and its built-in SQL rules. It does not contact the database.
  2. Test ConnectionConfirms that the configured server and database can be reached. It creates no documentation run.
  3. MetadataCreates a low-impact inventory of schemas, tables, columns, keys, indexes, and other structure.
  4. Metadata + LogicAdds static reading of views, procedures, functions, triggers, dependencies, and possible data flows. Nothing is executed.
  5. Safe ProfileAdds threshold-controlled statistics and masked samples. Review the run before creating a Git export.

Full Read-Only is optional: it performs the most complete scan and can use noticeable database CPU, I/O, and network capacity. Use it only after the earlier steps succeed and during an approved window.

What do these settings mean?

Sample rows limits how many example records can be collected per eligible object. Exact counts can be more expensive than estimates. Timeout stops an individual query from waiting indefinitely. Change configuration in the local .env file, then restart the UI.

Safety posture

Protection layers

ACTIVE
  • Only predefined SELECT queries are allowed
  • The Web server accepts local-machine traffic only
  • Actions require same-origin and CSRF checks
  • Sensitive profile and sample values are masked
  • Only one database job runs at a time
  • Git export repeats an independent evidence audit
Does read-only mean zero impact?

No. Read-only means the tool cannot intentionally insert, update, delete, execute procedures, or change schema. Profiling can still consume CPU, disk I/O, locks, and network bandwidth. Begin with Metadata and advance gradually.

Predefined actions

Choose one controlled action

Select one database to limit scope, or leave “All configured databases” to process them sequentially. The next database never starts until the current one finishes successfully.

Dry Run

Use first. Validates configuration and every built-in query against the read-only guard. No connection and no output folder.

Next: Test Connection.

Test Connection

Opens a short connection, checks identity/capabilities, rolls back, and closes it. No documentation run is created.

Next: Metadata.

Metadata

Inventories structural system catalogues only. It performs no table or view data scans and is the best first real run.

Next: review Output evidence.

Metadata + Logic

Adds stored definitions, static dependencies, and pipeline metadata. It performs no table/view data scans and never executes discovered code.

Next: review unknowns and access limits.

Safe Profile

Adds conservative bounded statistics, relationship checks, and masked table/view samples. Exact counts remain disabled.

Next: review masking and safety audit.

Full Read-Only

Adds separate larger bounded limits, extended validation, and optional exact counts under hard ceilings. It is the most resource-intensive mode.

Next: inspect the resolved policy, errors, coverage, and checksums.

Offline presentation refresh

Regenerate Reports

Choose one existing manifested output run. This action reads its canonical artifacts and creates a new versioned Markdown and HTML presentation without contacting SQL Server.

no database connection

The source run remains unchanged. Each request creates a separate folder under output/report_regenerations/ with its own manifest and checksums.

What this action does—and does not do

It rebuilds presentation files only from evidence already stored in the selected run. It does not query MSSQL, refresh metadata, profile data, repair missing evidence, overwrite the run, or create a Git-safe handoff. Review the regenerated report and use the separate Git-export workflow only for an approved canonical run.

Explicit handoff

Create a sanitized Git export

Output evidence is the local working record and may contain useful profile values. Git Export is a separate staged copy with stricter profile-value privacy for source control or handoff.

never automatic

The destination is created only after this explicit action applies the configured profile-value policy and passes containment, secret, profile, sample, and checksum checks. The source run is not modified.

When is a run ready to export?

Open its run details and review status, coverage, warnings, errors, masking state, and MASKING_SAFETY_AUDIT.json. Then inspect GIT_EXPORT_POLICY.json in the staged copy. A safe-to-commit checklist is supporting evidence, not proof that every local value is semantically de-identified. Historical runs produced before the masking repair must be re-run.
